# BookLeaf Portal — Approach

I prioritised the complete author-to-support loop: authors can sign in, review their own book and royalty records, submit a support ticket, and read staff replies. The operations team can triage tickets across authors, adjust category and priority, assign work, add private notes, and send an edited response. The supplied dataset is loaded into PostgreSQL so the portal works with books in production, zero sales, and unpaid royalties as well as live titles.

The active application uses Next.js App Router for its UI and REST handlers, Prisma ORM 7 for the data model, and Neon Postgres for persistence. Route handlers enforce session and role checks before reading or changing data. Session tokens are random, stored as hashes in the database, and sent in HTTP-only cookies. Author queries are scoped to the signed-in author; administrative queries require the admin role. Database access and secrets remain server-side.

Gemini handles ticket classification and response drafting. The draft prompt includes the relevant ticket, author, book and royalty context plus BookLeaf’s provided knowledge base. It asks for an empathetic, concise response, concrete next steps, and no invented account activity. The server sends only the selected case context rather than full ticket history. Classification and drafting degrade to deterministic rules/templates when Gemini is unavailable, and staff can edit every draft before sending.

Trade-offs: the deployed app uses a simple email/password session flow instead of a managed identity provider; avatars are small byte arrays in Postgres and are restricted to JPG/PNG/WebP files under 2 MB; and ticket views use a 10-second activity poll rather than push updates. Polling is a pragmatic fit for the current demo: it is straightforward to operate on Vercel, checks only a lightweight activity version, and pauses in hidden tabs. The trade-off is recurring database traffic from active pages and up to roughly 10 seconds of update delay. If active usage or the need for faster updates grows, replace polling with server-sent events or a managed realtime service. The admin queue supports date filtering and prioritizes unresolved tickets by urgency, then age. Sensitive writes use a database-backed fixed-window limiter with hashed client identifiers. Ticket attachments and malware scanning are deferred because the current app accepts only profile photos. Admins invite staff and authors by copying a generated link; transactional email is not connected. The app would benefit from managed authentication, a bot challenge if abuse warrants it, per-user storage quotas, and an evaluation set for AI accuracy and factuality as usage grows.
